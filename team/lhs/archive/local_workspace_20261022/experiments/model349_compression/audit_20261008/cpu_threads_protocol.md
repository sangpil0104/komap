# OpenCV 스레드 수 제한 보완 실험 (새 결과 전 고정)

01:35 UTC lite15의 width4000 B4 worker는 torch threads=2인데 프로세스 전체 스레드가 54개이며, 서버 loadavg는 84였다. GPU 7은 해당 worker 하나만 사용하는데 연산 점유가 낮고 이미지 시간이 늘어났다. 이는 OpenCV 기본 스레드 풀과 공유 CPU 경합이 병목일 가능성을 제시한다. 원인을 확정하지 않는다.

모델·TENT·해상도·계수는 바꾸지 않고 OpenCV를 2 threads로 명시 제한하는 별도 코드를 시험한다. PyTorch는 기존 2 threads를 유지한다. 기존 실행 코드나 진행 중인 실행은 수정하지 않는다. lite15 FP32, lite14 FP16 TENT5, 품질 통과 시 TENT3/12 조합에서 원본 valid20 전체를 다시 실행한다. 기존 코드와 마스크·공식 점수를 비교하고, 속도 판정은 같은 OpenCV 제한 조건의 lite15와 후보를 최소 3회 교차 측정한 중앙값·범위로만 한다.

스레드 제한만으로 모델 성능을 바꾸려는 실험이 아니며, 기존 FP16/TENT3의 평균 0.01%p·최악 0.10%p 손실 기준을 그대로 적용한다. 이 실험도 이미 반복 사용한 valid의 재현/탐색이며 독립 일반화 근거가 아니다.

실행 효율 보완: 진행 중인 default OpenCV lite15 기준은 완료까지 보존한다. 그 뒤 기존 기본 스레드 큐를 반복하지 않고, 별도 cpu2 코드로 lite15와 FP16/TENT3/12/10의 5개 초기 실행을 순차 진행한다. 초기 품질 통과 후보 중 가장 빠른 안을 고른 후, **기존 lite15 기본 OpenCV 전체 경로**와 해당 cpu2 후보를 각각 총 3회 이상 교차 실행하여 최종 목표(저장 크기와 실제 시간 모두 감소)를 판정한다. cpu2 lite15 초기 실행은 스레드 제한 효과 분리용이며, 최종 반복 속도 비교의 기준은 원래 lite15 기본 OpenCV다. 이는 모델 축소와 CPU 병목 개선을 합친 파이프라인 비교다. 12와 TENT3가 각각 품질 기준을 통과하면 12+TENT3 고정 결합을 한 번 추가 검증할 수 있다. 초기 시간에 따른 후보 선택은 반복 결과와 구분해 기록한다.

우선순위 보완: 사용자 추가 의견의 fold 선택 우려를 반영하여, 초기 5개와 사전 허용 결합은 진단으로 완료하되 그중 가장 빠른 fold 축소판을 기본 채택 대상으로 삼는 반복은 하지 않는다. 현재 실행은 보존하고 coordinator만 안전하게 교체한다. 최종 속도 반복 예산은 별도 사전 문서의 **전체 15개 모델을 보존한 FP16/D4batch4**와 원래 lite15에 집중한다. 초기 후보의 단회 시간을 개선 확정으로 표시하지 않으며, 품질 기준도 완화하지 않는다.
